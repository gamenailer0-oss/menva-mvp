# MENVA Instagram autoposter — code review

Scope: `social/n8n/src/*.js`, `social/scripts/build-workflow.mjs`, `social/server/*`, `social/templates/*`, and the calendar content files. Reviewed for correctness bugs and edge cases in a system meant to run **unattended for 200 days**. Read-only review, no files changed.

This review reflects the code *after* the in-progress fixes: `graphCall()` sending POST params as a form body, the `state.lock` publishing lock, the `build.js` media/attempts cleanup, and `install.sh` creating the n8n owner before Caddy goes public.

## Status after fixes (25 Sep 2026)

Fixed and tested against the mock Instagram: overlapping runs (a 30-minute publishing lock), media growth (images older than 30 days deleted, old retry counters pruned), captions and the token moved out of POST URLs (form body), an alert when a post is abandoned after 3 tries and when the calendar ends (each fires once), calendar offsets from the file name, a blank `.env` token no longer discards a working refreshed one, a damaged `state.json` is set aside and reported, the template can't be screenshotted after an error (a bad slide is refused in about 0.3 s), font-load failures become a clear error, no first-day token-refresh false alarm, `refreshedAt` only on a real new token, Story render retries, manual "Run now" on an already-posted day no longer triggers a dry-run alert, the firewall rules go before Oracle's REJECT rule, `update.sh` waits for an in-flight publish, a re-login hint for `docker` without sudo, and the n8n login is created before the dashboard goes public (plus 2FA advice in SETUP.md).

Not changed: alt text on carousel children (low; the API behaviour isn't confirmed), and the n8n editor staying on the public address (mitigated by the pre-created owner and 2FA; a VPN or IP allowlist would be the next step).

| Medium | `n8n/src/pick.js:36-37`, `n8n/src/build.js:10` (the new lock) | The lock is time-based, not liveness-based: `build.js` stamps `state.lock.at` once when a post starts and never refreshes it while genuinely still in progress; `pick.js` only treats the lock as stale after a **fixed 30 minutes**. | Medium | `n8n/src/lib.js:5-16` (`readCalendars`) | The day offset for file *i* is `i * 100` — computed from the file's **position** in the sorted `readdirSync` listing, not from the number in its filename, and with no check that each calendar file actually spans exactly 100 days. | Today this happens to work (`calendar.json` and `calendar-2.json` each run day 1–100, verified). | Medium | `n8n/src/publish.js:22-25` | `state.token` is only kept when `state.token.fromEnv === envToken.slice(-12)`. If `IG_ACCESS_TOKEN` in `.env` is ever accidentally blanked/corrupted (bad edit, failed `sed`) while a previously-refreshed token is cached in `state.token`, `envTag` becomes `''`, which won't match the stored `fromEnv`, so the code **overwrites** `state.token` with `{ value: '', ... }`, discarding the still-valid refreshed token. | An operator edits `.env` for an unrelated reason (e.g. changing `POST_TIME`) and a mistake leaves `IG_ACCESS_TOKEN=` empty; the currently-good refreshed token that was propping up posting gets thrown away, and posting breaks until someone notices and re-pastes a token. | Guard the reset with `if (envToken && (!state.token || state.token.fromEnv !== envTag))`, so an empty env value never overwrites a good cached token. |
| Medium | `n8n/src/lib.js:21-22` (`readState`) | `readState()` swallows *any* read/parse error and silently returns `{}` — no log, no alert. | If `state.json` is ever unreadable, the workflow loses `state.posted`, `state.attempts`, `state.token`, and now `state.lock` all at once with zero visibility. Losing `state.token` after a refresh means the next run falls back to the (possibly stale) `.env` token. | Medium | `social/server/install.sh:52-75` (owner setup) | The healthz wait loop (`for _ in $(seq 1 60); do ...; sleep 3; done`, 3 minutes max) doesn't check whether it actually succeeded before moving on to check `/rest/settings`. | Medium | `social/server/install.sh:22-27` | `sudo iptables -I INPUT 5 ...` hardcodes insertion position 5, assuming a specific default Oracle Ubuntu iptables ruleset. | On a Ubuntu 24.04 Oracle image whose default INPUT chain doesn't have ≥4 existing rules, `-I INPUT 5` errors out and (under `set -e`) aborts the whole install. ## Areas reviewed with no real issues found

- **Disk growth in `/files/media`**: `build.js` now deletes media files older than 30 days on every run and prunes `state.attempts` entries older than 7 days. This bounds growth to roughly a rolling month instead of accumulating unbounded across the full 200-day run. Good fix — verified the cleanup runs after `mkdir`, is wrapped in try/catch per file, and can't remove the current run's own (freshly-timestamped) files.
- **Caption length vs. URL limits**: `graphCall()` now sends all non-GET Graph API parameters (`caption`, `children`, `alt_text`, etc.) as an `application/x-www-form-urlencoded` body rather than a query string, removing the earlier risk of a ~2,200-character caption plus hashtags plus token pushing a POST request's URL past practical length limits.
- **Unclaimed n8n instance at install time**: `install.sh` now starts only `n8n`+`gotenberg` first, creates the owner account via `/rest/owner/setup` while Caddy (and thus the public 80/443 listeners) is still down, and only then brings Caddy up — closing the earlier window where a predictable `<ip>.sslip.io` domain could be raced by an attacker before the operator finished setup. (See the Medium finding above for the narrower residual case where the healthz wait times out silently.)
- **`.env`/repo exposure via Caddy**: the private `:8081` vhost is never published to the host (`docker-compose.yml` only maps `80`, `443`, `443/udp`), so it's unreachable from the internet regardless of its path allowlist; its allowlist also correctly excludes `.env` and defaults to `404`. The public vhost only serves `/media/*` and reverse-proxies everything else to n8n — no raw filesystem/`.env` exposure.
- **`N8N_ENCRYPTION_KEY` handling**: generated with `openssl rand -hex 24`, written once, file chmod'd `600`, never regenerated on re-run.
- **`git pull` vs. `files/` ownership**: `social/.gitignore` excludes `server/files/` entirely, so `git pull --ff-only` in `update.sh` never touches that directory regardless of any uid mismatch between the repo checkout owner and the `1000:1000`-owned files.
- **Carousel size limit**: `check-calendar.mjs` enforces `slides.length <= 10` at content-authoring time, matching Instagram's carousel limit.
- **Timezone/DST**: Asia/Karachi has no DST, and the timezone is set consistently (`GENERIC_TIMEZONE`/`TZ` in `docker-compose.yml`, workflow `settings.timezone`, and explicit `.setZone('Asia/Karachi')` calls in `lib.js`/`pick.js`) — no day-boundary drift risk from that source.
- **Calendar duplicate ids/days**: verified programmatically — no duplicate `id`, `day`, or `n` values within `calendar.json` or `calendar-2.json`, and the 100-day offset between the two files is currently consistent with their `day` ranges (both run 1–100).
- **Image save error handling**: the "Save image"/"Save story image" `readWriteFile` nodes rely on the HTTP node's default (non-`ignoreHttpStatusErrors`) behavior of throwing on a non-2xx Gotenberg response, so a Gotenberg error can't be mistakenly saved and published as if it were a valid JPEG.
